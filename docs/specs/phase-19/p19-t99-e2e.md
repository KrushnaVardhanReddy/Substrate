# Phase 19 — Task 99: E2E Validation (No Mocks)

## 1. Objective

Validate the complete Airbyte universal ingestion pipeline end-to-end using the existing
PGlite Go test harness. No mocks. The test must create a real source, ingest real records,
verify schema validation fires, and confirm MCP tools return accurate data.

## 2. Scope

All tests live in `scripts/e2e/phase19_e2e_test.go` and run against the standard
PGlite-backed API server used by the broader E2E suite (see `scripts/e2e/helpers.go`).

## 3. Go API Test Scenarios

### Scenario 1 — Source Lifecycle

```
POST /api/v1/org/test-org/airbyte/sources
  body: { "name": "Test HubSpot", "connector": "source-hubspot", "config": {"api_key": "test-key"} }
  assert: 201 Created, response body contains "id" (UUID)

GET /api/v1/org/test-org/airbyte/sources
  assert: 200 OK, array contains the created source with matching "name"

DELETE /api/v1/org/test-org/airbyte/sources/{id}
  assert: 204 No Content
  GET again → assert source is no longer in the list
```

### Scenario 2 — Record Ingestion & Violation Detection

1. Create a source and a stream contract via `POST /api/v1/org/test-org/airbyte/sources`.
2. Seed a stream contract (required fields: `customer_id`, `email`, `mrr`) via direct SQL
   into `stream_contracts` (acceptable for test setup only).
3. Ingest a batch of 3 records via `POST /api/v1/airbyte/ingest`:
   - Record 1: valid `{ customer_id: "c1", email: "a@b.com", mrr: 500 }`
   - Record 2: missing `mrr` → should generate a `HIGH` violation
   - Record 3: `mrr` is a string `"five-hundred"` → should generate a type violation
4. Wait 200ms for async validation goroutine to complete.
5. `GET /api/v1/org/test-org/airbyte/violations` → assert response contains exactly 2 violations.
6. Assert both violations appear in `insurance_claims` table with `claim_type = "stream_violation"`.

### Scenario 3 — MCP Tool: `configure_airbyte_source`

1. Open an MCP SSE session.
2. Call tool `configure_airbyte_source` with valid args.
3. Assert tool response contains `"id"` and `"name"`.
4. Assert a corresponding row exists in `airbyte_sources` DB table.
5. Call tool `list_airbyte_sources` → assert the new source appears.
6. Verify sensitive config fields are redacted in the `list_airbyte_sources` response:
   `api_key` value must equal `"[REDACTED]"`.

### Scenario 4 — MCP Tool: `get_airbyte_violations`

1. Using the violations seeded in Scenario 2, call MCP tool `get_airbyte_violations`.
2. Assert the response array has length ≥ 2.
3. Assert each item has `stream`, `field`, `severity` fields.

## 4. Constraints

- Do NOT mock the Airbyte ingest endpoint — test the real HTTP handler.
- All DB state assertions must query the actual Postgres tables via `db.QueryRow`.
- The test must call `t.Cleanup` to delete all seeded `airbyte_sources` rows after each scenario.
- Add `phase19_e2e_test.go` to `scripts/e2e/run_full_e2e.sh`.

2. MODIFY: `scripts/e2e/run_full_e2e.sh` — add `phase19` to the test run list
