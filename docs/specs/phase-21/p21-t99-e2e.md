# Phase 21 — Task 99: E2E Validation (No Mocks)

## 1. Overview

Validate the Kafka schema registry ingestion pipeline end-to-end against real PGlite:
source lifecycle, webhook ingestion triggering breaking change detection, MCP tool parity.

## 2. Test Scenarios

### Scenario 1: Source Lifecycle
1. `POST /api/v1/org/test-org/kafka/sources` → assert `201` + token returned.
2. `GET /api/v1/org/test-org/kafka/sources` → assert source appears.
3. `DELETE /api/v1/org/test-org/kafka/sources/{id}` → assert `204`.

### Scenario 2: Schema Version Ingestion (No Breaking Change)
1. Provision a token for `test-org`.
2. `POST /api/v1/kafka/schema-event` with v1 Avro schema (baseline `Payment` record).
3. Assert `202`. Assert `kafka_schema_versions` row exists for `payments-value@v1`.
4. `POST /api/v1/kafka/schema-event` with v2 adding a nullable field.
5. Assert `202`. Assert v2 stored. Assert no `events` breaking-change row created.

### Scenario 3: Breaking Change Detection
1. Post v1 schema (`Payment` with required `amount: int`).
2. Post v3 removing `amount` field entirely.
3. Assert `202`. Assert `events` row created with `type = kafka_breaking_change`.
4. `GET /api/v1/org/test-org/kafka/schemas/payments-value/diff?from=1&to=3` →
   assert response contains `FIELD_REMOVED` in the diff report.

### Scenario 4: MCP Tool Parity
1. Seed subject `payments-value` with 3 versions.
2. Call `list_kafka_subjects` → assert `payments-value` appears.
3. Call `get_kafka_schema_diff` v1→v3 → assert breaking changes present.
4. Call `get_kafka_breaking_events` → assert at least one event.

### Scenario 5: Auth Rejection
1. `POST /api/v1/kafka/schema-event` with no token → assert `401`.
2. `POST /api/v1/kafka/schema-event` with invalid token → assert `401`.

## 3. Rules

- No mocks. All assertions against real DB.
- Mirror structure of `phase19_e2e_test.go`.
- Use `require.NoError` for setup steps.
- `t.Cleanup` removes all `kafka_schema_sources` + `kafka_schema_versions` seeded per test.
