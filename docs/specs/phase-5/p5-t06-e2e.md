# P5-T06: Automated Dependency Discovery E2E Tests

## Overview
As per our Spec-First philosophy, this document defines the expected behavior and test strategy for the **Phase 5 Dependency Discovery Engine**. We need to prove that all the disparate scanners (Env Vars, Package Manifests, Terraform, Kafka, and OTel) can work together to build a highly accurate, cross-repo dependency graph without requiring developers to manually write `substrate.yaml` files.

## Test Strategy: The "Polyglot" Mock Repository

Instead of testing each scanner in isolation (which we already did via unit tests in P5-T01 to P5-T05), we will create a comprehensive end-to-end integration test inside `api/internal/discovery/e2e_test.go`. 

We will create a mock filesystem in `api/testdata/cross-repo-discovery/` that represents a complex microservice (e.g., `orders-service`) interacting with various downstream providers.

### Mock Filesystem Layout (`api/testdata/cross-repo-discovery/`)

```text
api/testdata/cross-repo-discovery/
├── docker-compose.yml           # Tests Env Var Scanner (injects PAYMENTS_API_URL)
├── package.json                 # Tests Package Scanner (depends on @myorg/auth-sdk)
├── openapitools.json            # Tests OpenAPI Generator Scanner (refs inventory-api)
├── terraform/
│   └── plan.json                # Tests Terraform Scanner (refs notifications-service URL)
├── asyncapi.yaml                # Tests Event-Driven Scanner (Kafka topic: orders.v2.created)
└── otel_traces.json             # Tests Runtime Confirmation (live trace to shipping-api)
```

### The E2E Test Execution Flow

The test `TestPhase5DependencyDiscoveryE2E(t *testing.T)` will perform the following steps:

1. **Initialize the Core:** Instantiate a new `Aggregator` (`discovery.NewAggregator()`).
2. **Register All Scanners:** Load the `EnvVarScanner`, `PackageScanner`, `OpenAPIScanner`, `TerraformScanner`, `EventScanner`, and `RuntimeScanner`.
3. **Execute Scan:** Pass the `cross-repo-discovery` mock directory to the aggregator's execution loop.
4. **URL Resolution Hook:** Provide a mock `URLResolver` that maps URLs to target repositories (e.g., maps `https://api.myorg.com/payments` to `myorg/payments-api`).
5. **Assert Graph Output:** Validate that the resulting `[]DependencyEdge` contains the exact expected edges, and that multiple signals overlapping (e.g., Static + Runtime) correctly boost the `Confidence` score.

## Expected Graph Assertions

The final aggregated dependency graph must resolve to the following edges:

| Source Repo | Target Repo | Detected Signal(s) | Expected Confidence |
|---|---|---|---|
| `myorg/orders-service` | `myorg/payments-api` | Env Var (`PAYMENTS_API_URL`) | 50 (Medium) |
| `myorg/orders-service` | `myorg/auth-sdk` | Package Manifest (`@myorg/auth-sdk`) | 80 (High) |
| `myorg/orders-service` | `myorg/inventory-api` | OpenAPI Generator Target | 90 (High) |
| `myorg/orders-service` | `myorg/notifications-service`| Terraform Output | 70 (Medium) |
| `myorg/orders-service` | `myorg/logistics-api` | Kafka Topic + OTel Trace | 100 (Capped) |
