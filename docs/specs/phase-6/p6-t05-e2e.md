# P6-T05: Phase 6 QA & Automation E2E Tests

## Overview
Following our Spec-First architecture, this document outlines the End-to-End (E2E) testing strategy for the **Phase 6 QA & Automation Layer**. Phase 6 introduced powerful features: Auto-updating Postman collections, Shadow API Coverage, Test Generation (fuzzing), and a Mock Server Time Machine. 

To prove these features work holistically without regressions, we must construct an integration test that chains them together in a real-world scenario.

## Test Strategy: The "QA Feedback Loop" Scenario

We will create a unified E2E test in `scripts/e2e/phase6_e2e_test.go` (or similar suite) that executes the complete QA lifecycle:

### Step 1: Mock Server Orchestration (P6-T04)
The test will invoke the `substrate mock` CLI command (using a fixture OpenAPI spec) to spin up a local mock server on a random port. This proves the time-machine feature works and provides a target for the next steps.

### Step 2: Auto-Test Generation (P6-T03)
The test will invoke the `substrate generate-tests` engine against the same fixture schema. We will assert that it successfully generates executable fuzzing payloads (JSON) based on the schema constraints (`maxLength`, `required`, etc.).

### Step 3: Fuzzing the Mock Server (Integration)
The test will execute the auto-generated HTTP payloads against the running Mock Server (Step 1). The mock server should successfully respond to valid fuzzing data and reject intentionally invalid generated payloads.

### Step 4: Shadow API Coverage (P6-T02)
During Step 3, the mock server (or a simulated OTel collector) will record the traffic. We will assert that the Shadow API Coverage analyzer successfully processes this traffic, maps it against the original schema, and correctly identifies which endpoints/fields were "Covered" and which were "Untested".

### Step 5: Postman Sync Webhook (P6-T01)
Finally, the test will synthesize an `APPROVED` webhook payload (simulating a schema update passing all tests) and send it to the Registry API's webhook handler. We will use a mocked `SyncClient` to assert that the integration attempts to sync the updated schema structure to the Postman API.

## Implementation Requirements (For Jules)
1. **No External Dependencies:** The mock server must run locally, and the Postman sync must use an `httptest.Server` or dependency-injected mock to avoid real network requests to Postman during CI.
2. **Deterministic Output:** The test generation fuzzing must use a fixed seed or predictable boundaries to ensure tests don't flake.
3. **Graceful Teardown:** The mock server must be cleanly shut down at the end of the test.
