TASK: P15-T02 — Granular GitHub Check Suite

═══════════════════════════════════════════════════════════════
OBJECTIVE
═══════════════════════════════════════════════════════════════
Replace the single monolithic "Substrate" GitHub CI check with highly granular, individually passable checks (e.g., `substrate / breaking-changes`, `substrate / schema-linting`) to match enterprise CI pipelines.

Spec (READ ONLY — implement from it, never edit):
  docs/specs/phase-15/p15-t02-granular-check-suite.md

═══════════════════════════════════════════════════════════════
CONSTRAINTS & RULES
═══════════════════════════════════════════════════════════════
- The GitHub App logic in `api/internal/github/checks.go` must dynamically create multiple checks based on config, instead of a single check.
- You must parse `substrate.yaml` bypass rules to determine if a check failure should be downgraded to `advisory/neutral`.
- Ensure backwards compatibility: if `substrate.yaml` has no granular check blocks, default to `blocking`.

═══════════════════════════════════════════════════════════════
CONTEXT — EXISTING REPO LAYOUT & ARCHITECTURE
═══════════════════════════════════════════════════════════════
GitHub integration logic is inside `api/internal/github/`.
Diff report data structures are shared via the `docs/contracts/core_models.md` specs.

⚠️ CRITICAL CONTEXT: MULTIPLE GITHUB CHECK RUNS ⚠️
Previously, `api/internal/github/checks.go` called `POST /repos/{owner}/{repo}/check-runs` once with name "Substrate".
You must refactor this to immediately POST 4 times to create 4 "queued" checks: `substrate/breaking-changes`, `substrate/security-rules`, `substrate/pii-compliance`, `substrate/schema-linting`.
Then, as diff results are bucketed, you must send 4 PATCH requests to conclude each check run independently.
