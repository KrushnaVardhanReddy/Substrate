TASK: P3-T02c — Cross-Repo Compatibility Check on PR

═══════════════════════════════════════════════════════════════
OBJECTIVE
═══════════════════════════════════════════════════════════════
When a provider repo opens a PR, the Cloudflare Worker must automatically
check whether the proposed schema change breaks any registered downstream
consumers. If it does, a cross-repo impact section is appended to the PR
comment AND the status check is marked as FAILING.

This is the most critical Phase 3 feature — the "killer" Cross-Repo Intelligence
capability that closes the gap between single-repo diff detection and full
engineering organization protection.

Spec (READ ONLY — implement from it, never edit):
  docs/specs/phase-3/contract-registry.md  (P3-T02c section, lines ~287–350)

Add the following TypeScript interfaces (do NOT remove any existing types):

  interface CrossRepoBreakingChange {
    rule: string;     // e.g. "ENDPOINT_MODIFIED"
    path: string;     // e.g. "GET /users/{id}"
    message: string;  // human-readable description
  }

  interface CrossRepoDiffSummary {
    breaking_count: number;
    warning_count: number;
    info_count: number;
  }

  interface CrossRepoDiffReport {
    breaking: CrossRepoBreakingChange[];
    warning: CrossRepoBreakingChange[];
    info: CrossRepoBreakingChange[];
    summary: CrossRepoDiffSummary;
  }

  interface ConsumerResult {
    consumer_repo: string;    // full_name e.g. "myorg/frontend"
    status: 'breaking' | 'safe' | 'warning' | 'unknown';
    diff_report: CrossRepoDiffReport;
  }

  interface CrossRepoCheckRequest {
    installation_id: number;
    org: string;
    provider_repo: string;          // full_name e.g. "myorg/backend-api"
    head_schema_content: string;    // raw schema content from PR head
    schema_type: string;            // openapi | graphql | sql | protobuf
  }

  interface CrossRepoCheckResponse {
    total_consumers: number;
    broken_consumers: number;
    is_safe: boolean;
    results: ConsumerResult[];
  }

  export function formatCrossRepoImpact(response: CrossRepoCheckResponse): string

  Implementation rules:
  - If response.total_consumers === 0, return an empty string "".
    (No consumers registered — do not add the section to the PR comment at all.)
  - Otherwise, generate this exact Markdown format:

  ---

  ## 🌐 Cross-Repo Impact

  This change affects **{total_consumers} registered consumer(s)**:

  | Consumer | Status | Breaking Changes |
  |---|---|---|
  | `myorg/frontend` | ❌ BREAKING | `GET /users/{id}` — field email removed |
  | `myorg/mobile-app` | ✅ Safe | No breaking changes detected |

  > ⚠️ **Action required:** Coordinate with the `myorg/frontend` team before merging.
  > The `substrate/breaking-changes` check is now **FAILING**.

  Formatting rules for the table rows:
  - For status === "breaking": use "❌ BREAKING"
  - For status === "safe": use "✅ Safe"
  - For status === "warning": use "⚠️ Warning"
  - For status === "unknown": use "❓ Unknown"
  - For the "Breaking Changes" cell: if breaking_count === 0, use "No breaking changes detected".
    If breaking_count > 0, show ONLY the FIRST breaking change formatted as:
      `{path}` — {message}
    If there are multiple breaking changes, append " (+N more)" at the end.
  - The action required callout at the bottom ONLY appears if broken_consumers > 0.
    List the broken consumer repos (joined by ", ") in the callout text.
  - If all consumers are safe (broken_consumers === 0), replace the callout with:
      > ✅ All registered consumers are compatible with this change.

FULL updated PR handler flow (steps that are NEW are marked with [NEW]):

  1. Parse PR event (existing)
  2. Fetch base and head schema files from GitHub (existing)
  3. Fetch substrate.yaml for schema_type, spec_path, config (existing)
  4. Call POST /diff on the diff engine (existing) → single-repo DiffReport
  5. [NEW] If REGISTRY_API_URL is set in env:
       Build CrossRepoCheckRequest:
         {
           installation_id: prEvent.installationId,
           org: prEvent.owner,
           provider_repo: prEvent.fullName,     // "myorg/backend-api"
           head_schema_content: <raw content of head schema file>,
           schema_type: <schema_type from substrate.yaml or detected>
         }
       Call crossRepoCheck(env.REGISTRY_API_URL, env.REGISTRY_API_TOKEN, request)
       → CrossRepoCheckResponse
     If REGISTRY_API_URL is NOT set, skip cross-repo check entirely:
       → use { total_consumers: 0, broken_consumers: 0, is_safe: true, results: [] }
  6. [NEW] Format cross-repo section:
       crossRepoSection = formatCrossRepoImpact(crossRepoResponse)
  7. Build PR comment body:
       comment = formatDiffReport(singleRepoDiffReport) + "\n" + crossRepoSection
       (if crossRepoSection is empty string, just use formatDiffReport result)
  8. Post PR comment (existing)
  9. [NEW] Determine overall status check result:
       - If singleRepoDiffReport has breaking changes → FAIL (existing behaviour)
       - [NEW] If crossRepoResponse.is_safe === false → FAIL
       - Otherwise → PASS
     The status check description should include cross-repo info if broken:
       "Breaking changes detected — {N} consumer(s) affected"
  10. Post GitHub status check (existing)

IMPORTANT: The REGISTRY_API_URL env var check (step 5) is the feature flag.
If the env var is missing/empty, cross-repo logic is completely skipped.
This ensures backward compatibility — existing GitHub Action users are unaffected.

CRITICAL IMPLEMENTATION RULES
═══════════════════════════════════════════════════════════════

1. NEVER block a PR based solely on a cross-repo registry error. If the Registry
   API is down or returns 5xx, log the error and treat the result as is_safe: true.
   The diff engine result (single-repo) is always the authoritative gate.

2. If REGISTRY_API_URL is not set in env, skip all cross-repo logic entirely.
   This is the feature flag for backward compatibility.

3. The head_schema_content sent to /api/v1/cross-repo-check must be the RAW file
   content of the schema at the PR's HEAD commit (not base). This is the exact
   content the Registry will diff against each consumer's stored snapshot.

4. The PR comment must always show the single-repo diff section first, then the
   cross-repo section below a horizontal rule separator. Never merge them.

5. The GitHub status check MUST fail if EITHER:
   a. Single-repo diff has breaking changes (existing behaviour), OR
   b. cross-repo-check returns is_safe: false (new behaviour)
   The status check description should clearly state which triggered the failure.
