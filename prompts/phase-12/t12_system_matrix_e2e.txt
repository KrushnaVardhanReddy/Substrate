OBJECTIVE
═══════════════════════════════════════════════════════════════
Implement a massive, parameterized Playwright End-to-End test suite that programmatically runs `git commit` and `git push` against our local Forgejo Git server. 
It must validate the Substrate Dashboard DOM updates in real-time via Server-Sent Events across ALL 7 schema types (OpenAPI, GraphQL, SQL, Protobuf, AsyncAPI) for Breaking, Safe, and Override scenarios.

═══════════════════════════════════════════════════════════════
CONSTRAINTS & RULES
═══════════════════════════════════════════════════════════════
- Do NOT use `page.route` to mock API responses. This is a true Integration test.
- Use `test.describe.serial` because the tests modify shared local Git repositories sequentially.
- Use a parameterized loop (`for (const repo of testMatrix) { ... }`) to iterate through the 7 repo configurations to keep the test DRY.
- Use Node's `child_process.execSync` to run `git push` commands.
- Ensure the tests can tolerate up to 10-15 seconds of latency for the webhook pipeline to complete before asserting the DOM. Set `test.setTimeout(120000)` at the suite level.

═══════════════════════════════════════════════════════════════
CONTEXT — EXISTING REPO LAYOUT & ARCHITECTURE
═══════════════════════════════════════════════════════════════
- The Playwright tests live in `dashboard/tests/e2e/`.
- The dashboard is accessible at `http://localhost:5173/org/admin/graph`.
- The 7 demo repositories are NOT fully committed to Git because they are gigabytes in size (e.g., Stripe API).
- Therefore, your Playwright script MUST dynamically write minimal "stub" schema files (e.g. 10 lines of OpenAPI, GraphQL, or SQL) into a `/tmp/<repo-name>-test` directory using `fs.writeFileSync`.
- Then use `execSync` to run `git init`, `git add .`, `git commit`, and set the remote to `http://admin:admin@localhost:3000/admin/<repo-name>.git` before pushing.
